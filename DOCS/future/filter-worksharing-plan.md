# Фильтры видов: слетают у других пользователей в файле-хранилище (отложено)

## Проблема

В workshared-модели (файл-хранилище): проектировщик работает с ранее созданным видом, другой пользователь в это время запускает «Сформировать виды». После отработки плагина фильтры слетают на виде проектировщика, хотя его виды явно не заменялись в окне конфликтов.

## Причина (подтверждена кодом и документацией Autodesk)

1. `OrchestratorService.GenerateViews` (строки 258–280): после создания видов идёт **безусловный** цикл по всем сборкам, не связанный с выбором в окне конфликтов.
2. `FilterService.CreateAssemblyFilter` / `CreateSectionMarkFilter` каждый раз **удаляют** существующий фильтр (`DeleteExistingFilter` → `doc.Delete`) и создают новый с **новым ElementId**. Удаление фильтра — элемента модели — снимает его со **всех** видов, где он был назначен (включая пропущенные и чужие).
3. Новый фильтр назначается заново (`ApplyFilterToView` → `view.AddFilter`) — это **изменение вида**. В worksharing вид, с которым работает проектировщик, принадлежит ему: по документации Autodesk «Revit views are also objects that can be claimed by a specific team member. Until they are released, they become uneditable for other users». Назначение на чужой вид отклоняется.
4. Ошибка глотается в `catch` с коротким Warn (FilterService.cs:95), `FailurePreprocessor` удаляет все предупреждения — конфликт остаётся невидимым.
5. Цикл «удалил → пересоздал → переназначил всем видам» существует потому, что после удаления фильтра восстанавливать привязки приходится всем видам сборки (см. `docs/realized/preserve-existing-views-with-conflict-dialog.md`, стр. 45). Само правило фильтра при этом не меняется — у сборки X оно всегда «скрыть всё, где группировка ≠ X».

## Решение

### Новая логика фильтров (устранение причины)

1. Фильтра `{Имя}_Фильтр` нет (новая сборка) → создать → назначить видам сборки.
2. Фильтр есть, набор категорий не изменился → **переиспользовать**: обновить правила на месте (`ParameterFilterElement.SetElementFilter(...)`), ElementId не меняется → привязки на всех видах сохраняются сами, виды (в т.ч. чужие) не трогаются. Новым (созданным в этом прогоне) видам — AddFilter.
3. Фильтр есть, набор категорий изменился (редко) → пересоздание с повторным назначением + громкое предупреждение про worksharing-последствия.
4. Фильтр меток разрезов `{Имя}_СкрытьЧужиеРазрезы`: категории (OST_Sections) и правило (имя вида не содержит `{Имя}_`) константы → создать, только если отсутствует.

### Диагностика (детальный лог + верификация)

| Событие | Уровень | Что пишется |
|---|---|---|
| Создание фильтра | Info | имя, ID, тип правила и значение, число категорий |
| Переиспользование/обновление фильтра | Info | имя + что обновлено (правила/ничего) |
| Удаление фильтра (при пересоздании) | Info | имя + старый ID |
| Назначение фильтра виду | Debug | имя фильтра + имя вида (успех — тоже) |
| Ошибка назначения | Warn | полное исключение (`ex.ToString()`) |
| **Верификация после назначения** | Warn | вид без фильтра / видимость не применилась / шаблон вида блокирует фильтры (имя шаблона; переиспользовать `ViewTemplateService.IsTemplateLockingFilters`) |
| Итог по сборке | Info | «сборка X: фильтр применён к N видам; отсутствует на: [...]» |
| Удаление видов (замена) | Info | каждый удалённый вид (`ViewService.DeleteViewsByNames`) |
| Применение шаблона вида | Debug | имя шаблона + флаг «контролирует фильтры» (`ViewService.ApplyViewTemplate`) |

Решение по самовосстановлению: **только лог**, без автоматического переназначения (сначала диагностика причины).

## Контрольный список ручной проверки (при реализации)

1. Два пользователя в файле-хранилище: проектировщик работает со своим видом, второй запускает «Сформировать виды» без замен → фильтры на виде проектировщика **не слетают**.
2. Повторный прогон без замен: в логе — «переиспользование/обновление фильтра», назначений на существующие виды нет, верификация без Warn.
3. Новая сборка: фильтр создан и назначен её видам.
4. Появление новой категории элементов: пересоздание фильтра с предупреждением; после переназначения фильтры на месте.
5. Шаблон вида, контролирующий «Фильтры», применён вручную к виду → повторный прогон → Warn с именем шаблона.
6. Переименование сборок — фильтры пересоздаются, лог детальный.
7. Сборка Debug.R21/R25 без ошибок.
