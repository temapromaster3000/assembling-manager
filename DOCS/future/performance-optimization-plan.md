# План оптимизации производительности массового создания видов

## Статус

`future` — реализация отложена на будущее.
Перемещение в `docs/realized/` выполнить только после успешного пуша соответствующих коммитов на GitHub.

## Проблема

Плагин Assembling Manager создаёт виды (план, 4 разреза, 3D) для каждой сборки (`AssemblyInstance`) в модели.

На тестовом проекте с 2 сборками всё работает мгновенно, но на реальном проекте с 50+ сборками и ~500 видами скорость катастрофически падает.

**Фактические замеры:**
- Создано видов: **324**
- Время работы: **599,10 с**
- Средняя скорость: **~1,85 секунды на вид**

Пользователь видит в строке состояния Revit, что каждый вид прогружается отдельно (`generating graphics`).

## Цель

Сократить время массового создания видов хотя бы в 2–3 раза, сохранив корректность:
- имён видов,
- CropBox / SectionBox,
- применения фильтров,
- обработки конфликтов (замена/пропуск существующих видов).

## Почему так происходит

### 1. Создание вида — дорогая операция в Revit

Каждый вызов:
- `ViewPlan.Create`
- `ViewSection.CreateSection`
- `View3D.CreateIsometric`

заставляет Revit построить графику вида. В большой модели это занимает заметное время. Транзакция откладывает запись изменений в модель, но **не откладывает генерацию графики** вида.

### 2. Применение фильтров к видам дорогое

`view.AddFilter` + `view.SetFilterVisibility` заставляют вид пересчитать видимость элементов по правилу фильтра. На большой модели это заметно замедляет процесс.

### 3. Повторные поиски по всему документу

Для каждого вида/сборки заново ищутся:
- `ViewFamilyType` (план, разрез, 3D),
- нулевой уровень (`GetOrCreateZeroLevelId`),
- существующий вид по имени (`GetViewByName`),
- список видов сборки (`GetExistingAssemblyViews`).

`FilteredElementCollector` быстрый, но на сотнях видов накладные расходы суммируются.

### 4. LINQ и материализация коллекторов

В нескольких местах используются `.ToList()`, `.ToElements()`, `.Cast<T>().Where(...)` и LINQ-постобработка на стороне .NET. Это заставляет Revit передавать больше данных в .NET, чем необходимо.

### 5. Нет индикации прогресса

Пользователь не видит, что процесс идёт, и воспринимает ожидание как зависание.

## Планируемые изменения

### Этап 1. Профилирование (1 коммит)

Добавить в `OrchestratorService.GenerateViews` замеры `Stopwatch` для каждой фазы:

1. Подготовка: сборка элементов, категорий, параметров.
2. Создание всех видов (по типам: план, фасады, разрезы, 3D).
3. Создание фильтров.
4. Применение фильтров к видам.

Результат: точное понимание, куда уходит 80% времени. Это позволит скорректировать дальнейшие этапы.

### Этап 2. Быстрые оптимизации (1–2 коммита)

**Кэширование:**
- `ViewFamilyType` для `FloorPlan`, `Section`, `ThreeDimensional` — получить один раз.
- ID нулевого уровня — получить один раз.
- Словарь существующих видов `Dictionary<string, ElementId>` — собрать один раз в начале `GenerateViews`.

**Убрать лишние операции:**
- Заменить `GetViewByName` на поиск по кэшированному словарю.
- Заменить `GetExistingAssemblyViews` на фильтрацию по кэшу.
- Убрать лишние `.ToList()` и `.ToElements()` у `FilteredElementCollector`.
- Для применения фильтра использовать только `SetFilterVisibility` (документация Revit API: `AddFilter` вызывается неявно, отдельный вызов не обязателен).

### Этап 3. Дублирование вида вместо создания с нуля (1 коммит, потенциально самый эффективный)

Опыт других разработчиков Revit API показывает: **`View.Duplicate(ViewDuplicateOption.Duplicate)` работает заметно быстрее, чем `CreateIsometric`**. Для планов и разрезов дублирование также может быть быстрее, чем создание с нуля.

**Подход:**
1. Создать один «мастер-вид» каждого типа:
   - план,
   - фасад спереди,
   - фасад сзади,
   - вид справа,
   - вид слева,
   - 3D вид.
2. Для каждой сборки **дублировать** мастер-вид, переименовать, подогнать рамку (CropBox / SectionBox).
3. Мастер-вид можно сделать скрытым или удалить в конце.

**Риски:**
- Не все виды можно дублировать с помощью `View.Duplicate` (нужно проверять `CanViewBeDuplicated`).
- При дублировании могут скопироваться аннотации, легенды, настройки шаблона вида. Нужно сбросить их, если они не нужны.
- Для 3D вида `SectionBox` при дублировании может сохраниться — нужно переустановить под сборку.
- Требуется проверка, что `CropBox` и `SectionBox` корректно обновляются после дублирования.

**Проверка:** протестировать на небольшом проекте (2–5 сборок) перед применением на большом.

### Этап 4. Отложенное применение фильтров (1 коммит)

Сейчас последовательность уже разделена:
1. Создание всех видов.
2. Создание фильтров и применение к видам.

Можно ещё сильнее разделить:
1. Создание всех видов.
2. Создание всех фильтров.
3. Применение всех фильтров ко всем видам — **самым последним шагом**.

Это уменьшит вероятность промежуточной перегенерации вида.

### Этап 5. UI: окно прогресса (1 коммит)

Добавить WPF-окно с прогресс-баром и текстом:
- «Создание видов: 47 из 324»
- «Применение фильтров: 12 из 54»

Окно не ускоряет код, но позволяет пользователю понимать, что процесс идёт, и оценить оставшееся время.

## Риски и ограничения

- **Revit API не позволяет полностью отключить генерацию графики.** Некоторое время на создание вида неизбежно.
- **Дублирование видов** — самый перспективный путь, но требует тщательного тестирования, особенно для 3D видов и разрезов.
- **Многопоточность недоступна.** Revit API строго однопоточный.
- **Разбиение на несколько транзакций** было опробовано (партии по 10 сборок) и не дало прироста; время даже немного выросло. Возвращено к одной транзакции внутри `TransactionGroup`.

## Подготовка
- [ ] Создать ветку/рабочую копию для оптимизации.
- [ ] Подготовить тестовый проект: 2–5 сборок (для быстрой проверки логики).
- [ ] Подготовить реальный проект: 50+ сборок (для финального замера).

### Реализация
- [ ] Этап 1: профилирование — добавить Stopwatch и сохранить в `ViewCreationResult`.
- [ ] Этап 2: файловое логирование — добавить `Logger` для записи замеров.
- [ ] Этап 3: дублирование видов (с фолбэком на старое создание при невозможности дублирования).
- [ ] Этап 4: окно прогресса.

### Ручная проверка (на тестовом проекте)
- [ ] Все виды создаются с правильными именами (`<ИмяСборки>_План`, `_Вид спереди`, ...).
- [ ] Плановый вид имеет корректный `CropBox` и `ViewRange`.
- [ ] Разрезы и фасады имеют корректный `SectionBox`.
- [ ] 3D вид имеет корректный `SectionBox`.
- [ ] Фильтры корректно скрывают элементы, не принадлежащие текущей сборке.
- [ ] Повторный запуск корректно пропускает существующие виды или заменяет их, если пользователь выбрал замену.

### Ручная проверка (на реальном проекте)
- [ ] Время создания ~500 видов сократилось хотя бы в 2 раза по сравнению с 599 секундами.
- [ ] Все виды создались без ошибок.
- [ ] Фильтры работают корректно на всех видах.
- [ ] Revit не падает и не зависает на середине процесса.
- [ ] Окно прогресса отображает текущий статус и корректное общее количество видов.
