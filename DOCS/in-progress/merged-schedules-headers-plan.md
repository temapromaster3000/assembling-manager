# Заголовки спецификаций при объединении (модуль «Проставить позиции»)

## Проблема

При объединении спецификаций («сквозная нумерация») проектировщик получает на листе несколько кусков таблиц, которые нужно соединить вручную, при этом каждый кусок никак не подписан — непонятно, где чья сборка. Плюс подписи столбцов в заголовках могут содержать случайный текст.

## Цель

Когда в модуле «Проставить позиции» реально включено объединение (галочка «Объединить спецификации» + выбрано больше одной спецификации + найден параметр `ADSK_Наименование`), внутри той же транзакции:

1. У **всех** выбранных спецификаций включить «Показать заголовки столбцов» (`ScheduleDefinition.ShowHeaders = true`).
2. Во всех заголовках **безусловно очистить подписи всех столбцов** (стираем любые заполненные значения).
3. В подпись столбца **ADSK_Наименование** записать **имя сборки** (имя спецификации без суффикса «_Спецификация» — совпадает со значением фильтра).
4. **Первой** спецификации в списке — включить «Показать название» (`ShowTitle = true`), текст названия не трогать (там уже будет имя вида); **остальным** — выключить (`ShowTitle = false`).

Итог: куски спецификаций на листе подписаны именами сборок в столбце «Наименование», проектировщику остаётся соединить их в одну таблицу.

## Технические решения

- Видимость заголовков — `ScheduleDefinition.ShowHeaders` / `ShowTitle`; временных включений/выключений не требуется: текст и видимость заголовка независимы.
- Подписи столбцов — через свойство **`ScheduleField.ColumnHeading`** (сеттер): среди видимых полей (`Definition.GetFieldOrder()`, скрытые пропускаются — они не рисуют колонок) **третьему по порядку** назначается имя сборки, остальным — пустая строка. Секция `SectionType.Header` (блок названия) **не затрагивается вовсе**.
- Целевой столбец — фиксированно третий видимый: в спецификациях пользователя параметр `ADSK_Наименование` скрыт, а третий столбец — комбинированное поле (у него пустой `ParameterId`, поэтому сопоставление по параметру невозможно). Привязка к порядковому номеру хрупкая: при изменении структуры спецификаций целевой столбец сместится — факт записи фиксируется в Debug-логе (номер столбца и имя поля).
- Если видимых столбцов меньше трёх — предупреждение в отчёт, очистка не выполняется.
- Производительность: запись в поля — обычная модельная запись внутри уже открытой транзакции (доли мс на спецификацию), дополнительной регенерации не требуется.
- Защита: пер-полевой try/catch (нестандартные поля не роняют команду), предупреждения попадают в отчёт.

## Регрессия первых версий (исправлена)

Версия 1 писала подписи столбцов через `GetSectionData(SectionType.Header).SetCellText(...)`, исходя из неверного предположения, что Header-секция содержит заголовки столбцов. На самом деле (подтверждено Дж. Таммиком и форумом Revit API):

- `SectionType.Header` — это **только блок названия** спецификации;
- заголовки столбцов рендерятся в **Body**-секции, где `SetCellText` для стандартных спецификаций **запрещён** («forbidden for cells in standard schedule body sections»).

Следствия: стирался пользовательский текст названия (очистка последней строки Header-секции) и не записывалось имя сборки (в секции названия нет параметров столбцов — колонка «не находилась»). 

Версия 2 искала поле по совпадению `ScheduleField.ParameterId` с ID параметра `ADSK_Наименование` — но в спецификациях пользователя это поле скрыто, а видимый третий столбец — комбинированное поле без `ParameterId`. Исправление: Header-секция не трогается, подписи — через `ColumnHeading` третьего видимого столбца.

## Реализация

1. **`Services/ScheduleService.cs`** — новые методы:
   - `ApplyMergedScheduleHeaders(schedules, warnings)` — ShowHeaders/ShowTitle по индексу (первый — с названием);
   - `ApplyMergedColumnHeadings(...)` — третий видимый столбец получает имя сборки, остальные очищаются.
2. **`Commands/AssignAssemblyPositionsCommand.cs`** — вызов `ApplyMergedScheduleHeaders` внутри транзакции в блоке `mergedState != null` (после цикла `ProcessSchedule`, до `document.Regenerate()`); предупреждения — в общий список отчёта.

## Контрольный список ручной проверки

1. Подготовить модель: 2–3 сборки, у каждой своя спецификация, размещённые на листах куски.
2. «Проставить позиции» → выбрать спецификации → включить «Объединить спецификации» → Выполнить.
3. Проверить: позиции сквозные (как раньше); у всех выбранных спецификаций показаны заголовки столбцов; подписи столбцов очищены, кроме **третьего видимого столбца** (комбинированное поле) — там имя сборки.
4. Первая спецификация в списке — с названием (текст названия не изменился), остальные — без названия.
5. На листе куски соединяются в одну таблицу, каждый подписан своей сборкой.
6. Без галочки объединения — заголовки спецификаций не меняются (прежнее поведение).
7. Если в заголовках столбцов был свой текст — он стёрся (безусловная очистка).
8. «Отмена» в диалоге — модель не меняется; отчёт/лог без ошибок; при нестандартных полях — предупреждения в отчёте; в Debug-логе видно, какому столбцу (номер и имя поля) досталось имя сборки.

Примечание: семантика пустой строки в `ColumnHeading` требует проверки — Revit может показать пустую ячейку или откатиться к стандартному имени параметра. Если вместо пустых подписей отображаются имена параметров — сообщить, обсудим желаемое поведение.
