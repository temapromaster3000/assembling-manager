# План: модуль «Оси трубопроводов»

Статус: в реализации. Модуль строит осевые линии трубопроводов на планах и разрезах сборок
аннотационными линиями, чтобы оси были видны при дисциплине вида «Координация» без включения
режима «Механизмы» (при котором все элементы просвечивают).

## Обоснование (исследование 09.09.2026)

- В дисциплине «Координация» Revit нативно не показывает оси труб; в дисциплинах MEP оси видны,
  но все элементы теряют скрытие линий (труба над трубой просвечивает). Это ограничение Revit,
  подтверждено форумами Autodesk (2018–2026), заявка в Autodesk Ideas висит с 2016 года.
- Сообщество решает проблему вручную: рисует осевые аннотационные линии привязкой к трубе.
  Готового плагина, автоматизирующего это, не найдено (ModPlus делает только осевые размеры/отметки).
- Техническая база: `Document.Create.NewDetailCurve(view, curve)` — кривая должна лежать в плоскости
  вида (The Building Coder, посты 0214/0358/1754). Проекция через `View.CropBox.Transform`
  (нулевой глубины) работает и для планов, и для разрезов; для планов есть fallback на `SketchPlane`.

## Сценарий работы

1. Команда «Оси трубопроводов» на панели ленты «Оформление».
2. Окно: список сборок с чекбоксами (мультивыбор, поиск, «Выбрать всё»), выпадающий список
   **существующих стилей линий** проекта (подкатегории категории «Линии»),
   кнопки **«Нанести оси»**, **«Удалить оси»**, «Отмена».
3. Для каждой выбранной сборки модуль находит её виды по именам (как в `NeighborAxesService`):
   - план = имя сборки (`ViewService.GetViewByName` + `typeof(ViewPlan)`);
   - разрезы = имя + суффиксы `_Вид спереди/_Вид сзади/_Вид справа/_Вид слева`.
4. В каждом виде: удалить свои старые линии (опознаются по выбранному стилю) и нарисовать заново
   осевые трубы, видимые в этом виде (`FilteredElementCollector(doc, view.Id)` +
   `OST_PipeCurves` + `Pipe`).
5. «Удалить оси» — только убрать линии выбранного стиля в видах выбранных сборок.
6. Итоговый отчёт (TaskDialog): обработано видов, создано/удалено линий, найдено/пропущено труб,
   предупреждения, время.

## Правила геометрии

- Ось трубы берётся из `Pipe.Location` (`LocationCurve.Curve`, для v1 — только прямая `Line`).
- Концы оси проецируются в координаты вида (`CropBox.Transform.Inverse`), глубина отбрасывается
  (Z=0), точки отображаются обратно в мировые → линия гарантированно параллельна плоскости вида.
- **Порог минимальной длины проекции — 20 мм (модельных).** Проекция короче (стояки на планах,
  трубы вдоль взгляда на разрезах) или точка → пропуск + запись в отчёт/лог.
  Уклон самих труб не проблема: наклонная труба на плане/разрезе даёт нормальную линию проекции.
- Стиль линии присваивается через `DetailLine.LineStyle`; стиль служит «меткой» для обновления
  и удаления.

## v1.1 — пропуск перекрытых участков (09.09.2026)

Аннотационные линии всегда рисуются поверх модели, поэтому ось перекрытой трубы «протыкает»
скрывающие её элементы. Добавлена проверка перекрытий лучами (`ReferenceIntersector`):

1. Виды обрабатываются парами «сборка + вид»; перекрывателями считаются только элементы
   своей сборки (в виде сборки остальное не видно).
2. Внутри транзакции создаётся временный 3D-вид (`View3D.CreateIsometric`, типоразмер
   `ViewFamily.ThreeDimensional`), используется для `ReferenceIntersector`, в конце удаляется;
   при откате транзакции исчезает сам. Существующие 3D-виды не трогаем: у них может быть
   активный секущий бокс (ломает лучи) и скрытые категории.
3. Один раз собирается словарь изоляции: `InsulationLiningBase.HostElementId` → id изоляций.
4. Для трубы цели луча = элементы сборки − сама труба − её изоляция; конструктор
   `ReferenceIntersector(ICollection<ElementId>, FindReferenceTarget.Face, view3D)`.
   Изоляция чужих труб и любые другие элементы честно перекрывают.
5. Вдоль оси 5–50 проб (шаг ≈25 мм проекции, точки в центрах ячеек `(i+0.5)/n`); из каждой
   — `FindNearest(точка, view.ViewDirection.Normalize())`. `ViewDirection` по докам 2021 —
   «direction towards the viewer», луч идёт вдоль него без инверсии.
6. Попадание = перекрытие. ~~Точка попадания дополнительно проверялась на «внутри
   обрезки вида» по X/Y/Z~~ — **в v1.2 этот фильтр удалён**: Z-границы `CropBox`
   у плановых видов в Revit ненадёжны (известная причуда), из-за чего легитимные попадания
   (например, труба выше секущей плоскости плана) отбрасывались и перекрытия не
   засчитывались вовсе. Луч перпендикулярен виду, X/Y попадания всегда совпадают с пробой,
   поэтому фильтр не нёс пользы. Остаточный риск: элемент «за дальним клипом» может
   ложно перекрыть — для малых сборочных видов принят как допустимый.
   Диагностика: в лог по каждому виду пишется «rays / hits»; если лучи пущены, а попаданий
   0 — явное предупреждение (сигнал проверять видимость категорий во временном 3D-виде).
7. Маска «видимо/скрыто» → непрерывные видимые интервалы (границы ячеек `a/n..(b+1)/n`);
   для каждого интервала длиной ≥ 20 мм создаётся отдельная линия. Нет интервалов → труба
   полностью перекрыта (счётчик в отчёте).
8. Выключатель в окне: чекбокс «Пропускать перекрытые участки» (по умолчанию вкл,
   хранится в пресете). Выключен → ось рисуется целиком, лучи не пускаются.

Известный риск: если знак `ViewDirection` в живом Revit окажется противоположным,
симптом — «оси пропали у всех труб разом». Правка — один знак в коде.
Подтверждено логом 09.09.2026: знак верный (у разрезов `ViewDirection` = минус базису
секущего бокса, т.е. к зрителю).

## v1.3 — временный 3D-вид не видел геометрию членов сборок (09.09.2026)

Лог v1.2: 3497 лучей → 23 попадания ≈ ноль. `ReferenceIntersector` видит только то,
что видимо в переданном 3D-виде; временный вид создавался с настройками по умолчанию.
Страховки v1.3:

1. `DetailLevel = Fine` принудительно (при грубой детализации MEP-геометрия не генерируется —
   известная причина пустых результатов).
2. Стадия и фильтр стадии копируются из обрабатываемого 2D-вида (`VIEW_PHASE`,
   `VIEW_PHASE_FILTER`, защитно).
3. Члены сборки разворачиваются рекурсивно (вложенные `AssemblyInstance` → их члены,
   контейнеры без геометрии в цели не попадают).
4. Скрытые во временном виде члены показываются (`View.UnhideElements`, только реально
   скрытые, с регенерацией).
5. Зонд-диагностика для вида с нулевыми попаданиями: по первой трубе логируются
   `IsHidden(rayView)`, `Find()` без фильтра вперёд/назад (что вообще видно интерсектору,
   с id, категориями и дистанциями), `Find()` с членами вперёд/назад, размер целей.
   Если после страховок 1–4 перекрытия всё ещё не работают — лог зонда однозначно
   укажет оставшуюся причину.

## v1.4 — интерсектор на 3D-вид сборки (09.09.2026)

Временный 3D-вид упразднён; перекрытия проверяются в **собственном 3D-виде сборки**
(тот, что создаёт главный модуль «Сформировать виды», имя = имя сборки):

1. Для каждой сборки ищется её 3D-вид; годится только View3D, не шаблон, не перспектива.
   Не найден → перекрытия для сборки пропускаются, оси строятся целиком, в отчёт
   предупреждение с инструкцией (создать 3D-вид и повторить запуск).
2. **Один `ReferenceIntersector` на сборку** (цели = развернутые члены сборки), обслуживает
   все 5 видов сборки; свои попадания (труба + её изоляция) отбрасываются в коде через
   `Find()` вместо `FindNearest` — убраны перпайповые интерсекторы (главная статья времени).
3. **Быстрый путь**: габариты членов берутся через `get_BoundingBox(вид)` и сравниваются
   с 2D-коробкой оси трубы (с запасом на диаметр); нет кандидатов → ось целиком, ноль лучей.
4. Никаких мутаций видов пользователя: без копирования стадий, скрытий и детализации.
   В лог (раз на сборку): имя 3D-вида, стадия, детализация, число целей.
5. Секущий бокс 3D-вида сборки ограничивает лучи рамкой сборки — перекрыватели (члены
   той же сборки) всегда внутри, потерь нет.

## v1.5 — убран «быстрый путь», добавлены измерения (09.09.2026)

Лог v1.4 вскрыл регрессию: в v1.4 лучи пускались не всем трубам — «быстрый путь»
сравнивал контур оси с габаритами членов через `get_BoundingBox(вид)` и пропускал
трубы «без кандидатов». Для разрезов `get_BoundingBox` отдаёт габариты в искажённых
координатах (известная причуда Revit), из-за чего реально перекрытые трубы
классифицировались как «без кандидатов» и рисовали оси целиком — оси, которые v1.3
корректно резала, снова появились. Доказано зондом: у трубы в «Виде слева» были
попадания на зонде (@2307 мм), но в основном потоке ей не пустили ни одного луча.

1. **Быстрый путь удалён** — лучи снова пускаются всем видимым трубам (скорость и так
   ~18 с на прогон после «одного интерсектора на сборку», оптимизация не стоила бага).
2. **Разгадка «дублей» 16:40**: пользователь нажимал Ctrl+Z между прогонами «Нанести
   оси» — отмена транзакции убирала линии первого прогона, поэтому второй прогон
   находил 0 линий к удалению. Бага в удалении нет; дубли не образуются при обычном
   повторном запуске без Ctrl+Z.
3. **Диагностика без вмешательства** (стадии пользователь подтверждает одинаковыми,
   копирование не делаем — только факты в лог):
   - на каждый вид: стадия и фильтр стадии 2D-вида и 3D-вида рядом;
   - зонд запускается на КАЖДОМ виде (раньше — только при нулевых попаданиях, из-за
     чего план остался без снимка);
   - счётчик «труб(ы) вне членов сборки» (в норме 0; если > 0 — предупреждение в отчёт).

## v1.6 — многопроходный пуск лучей по стадиям (10.09.2026)

Эксперимент пользователя (два одинаковых листа, отвод над трубой):
- отвод в стадии «Новая конструкция» → ось трубы корректно порезана;
- отвод в стадии «Существующая» → ось нарисована поверх отвода.
Лог v1.5 подтвердил: стадия и фильтр у 2D и 3D видов идентичны
(«Новая конструкция» / «Показать все»), пользователь видит отвод на 3D-виде.

**Вывод: `ReferenceIntersector` применяет к стадиям другую логику, чем отображение
вида** — он находит только элементы, созданные в стадии вида, игнорируя фильтр
«Показать все» (который в отображении показывает и предыдущие стадии). Не отражено
в документации API; правило выведено из эксперимента.

**Решение**: лучи пускаются по одному проходу на каждую уникальную стадию членов
сборки (`CreatedPhaseId`):
1. Для сборки собираются уникальные стадии её членов (обычно 1–2).
2. На каждый проход: 3D-виду сборки временно ставится стадия прохода, регенерация,
   интерсектор, прогоны лучей всех видов сборки с накоплением масок (образец уже
   закрытый в предыдущих проходах не пересчитывается — экономия лучей).
3. После проходов стадия 3D-вида восстанавливается (try/finally; при сбое транзакция
   откатит и это).
4. Линии создаются один раз — по объединённой маске.
5. Сборка с одной стадией работает как раньше (один проход).
6. Зонд срабатывает на каждый вид и проход с нулевыми попаданиями (в логе отмечен
   номер прохода и стадия).
7. Подход устойчив к обоим вариантам внутренней логики интерсектора
   («создан в стадии вида» или «создан не ранее»): ранние проходы уже видят всё
   нужное, поздние добавляют мало лучей.

## v1.7 — цели лучей = всё видимое на виде (10.09.2026)

Эксперимент пользователя: отвод в стадии «Существующая» перекрывал трубу, но ось
рисовалась поверх; перевод отвода в «Новую» и многопроходный механизм (v1.6) не
помогали. Проверка в Revit: отвод **не член сборки** — он виден на видах через
параметр «Добавить существующее» (фильтр видов пропускает его), а цели лучей
строились из `GetMemberIds()` (только истинные члены) → лучи проходили сквозь него.

1. Цели лучей = все элементы, видимые в 2D-виде (`FilteredElementCollector(doc,
   view.Id)`), минус элементы без тел (линии детализации, текст, размеры, уровни,
   оси) и минус сама труба с её изоляцией. Семантика: «ось перекрывает всё, что
   видно на листе» — независимо от членства в сборке.
2. Интерсектор на пару «вид × проход»; проходы по стадиям (v1.6) сохранены — стадии
   собираются из видимых целей.
3. Никаких мутаций вида: стадия переставляется только при несовпадении с текущей
   (v1.6-механизм с восстановлением), бокс не трогается (в логе — его состояние).
4. Зонд и диагностика сохранены.

## Ограничения v1

- Только трубы текущей модели (связанные модели — v2); фитинги не рисуются (оси сегментов
  стыкуются на фитингах); только прямые трубы `Pipe` (гибкие/дуговые — v2, с тесселяцией);
- 3D-виды не поддерживаются (только планы и разрезы);
- оси статичны: после сдвига трубы нужен повторный запуск «Нанести оси» (обновление);
- если пользователь сменил стиль линии между прогонами, линии старого стиля не удаляются
  автоматически (удаляются только линии выбранного стиля);
- перекрытие проверяется только элементами своей сборки (в виде сборки остальное и так
  не видно); попадания за обрезкой вида игнорируются.

## Кандидаты в v2

- Условный знак в точке проекции: кружок с точкой («на нас») / с крестом («от нас»).
- Порог минимальной длины проекции как настройка в окне.
- Гибкие и дуговые трубы (тесселяция), воздуховоды, связанные модели.
- Автообновление осей (DMU / DocumentChanged).

## Контрольный список ручной проверки (в Revit)

1. Открыть модель со сборками, содержащими трубопроводы; дисциплина видов «Координация».
2. Запустить «Оси трубопроводов», выбрать 2–3 сборки и стиль линии → «Нанести оси»:
   на планах и разрезах появились осевые линии выбранным стилем; трубы НЕ просвечивают;
   дисциплину вид не менялся.
3. Сдвинуть трубу в сборке → повторный запуск (та же сборка, тот же стиль) → ось переместилась,
   дублей нет.
4. «Удалить оси» → линии исчезли только в видах выбранных сборок.
5. Сборка без труб / без видов → строки-предупреждения в отчёте, плагин не падает.
6. Второй прогон с другим стилем → линии старого стиля не тронуты, новые в новом стиле.
7. Вертикальные стояки на планах и трубы вдоль взгляда на разрезах → пропущены,
   в логе/отчёте есть счётчик пропусков.
8. Труба под уклоном → ось рисуется корректной линией проекции.
9. Осевые линии не попадают в другие виды и спецификации (аннотации привязаны к виду).
10. Перекрытия: труба за трубой → ось задней трубы не рисуется; труба частично за стеной →
    ось рисуется только видными кусками; изолированная труба → ось целиком.
11. Труба с собственной изоляцией → ось рисуется (свою изоляцию проверка игнорирует).
12. Чекбокс «Пропускать перекрытые участки» выключен → оси рисуются целиком как в v1.0.
13. Если после обновления оси пропали у ВСЕХ труб (в т.ч. заведомо видимых) — вероятен
    обратный знак `View.ViewDirection`: сообщить разработчику (правка одного знака).
14. Время работы в отчёте не деградировало заметно (лучи добавляют доли секунды на вид).
    Замечено: v1.1 на ~10 видов работала ~3 минуты (перпайповые интерсекторы + генерация
    графики 3D-вида). Оптимизация (один интерсектор на вид + `Find` с фильтрацией своих
    попаданий) запланирована после подтверждения корректности перекрытий.
